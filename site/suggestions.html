Suggestions & open questions

Nothing here is decided for you. Below is the list of questions that need answers before a decision can be made, what we have and do not have, and the suggestions for discovering what is missing. Review, pick a path, then implement.

Open questions to resolve first

Question Q1

Do we keep the submitted link.amazon short links, or replace them with tagged Special Links generated in the Associates console?

What we know: All five submitted links resolve to real Amazon listings. Each submitted token is a 9-character short-link token, not a 10-character ASIN. Program Policies 6(w) prohibits using link shortening in a way that makes the Amazon destination unclear. The exact compliance status of the supplied short links is unresolved.

What we do not know: Whether the enrolled Associates account exists and can generate tagged Special Links for these five ASINs; Amazon's specific determination of these short links.

Options

  • Replace with tagged Special Links — Most compliant and trackable; requires an enrolled Associates account and a one-link-per-product test in the enrolled workflow.
  • Keep short links with explicit Amazon disclosure — Fastest; carries unresolved 6(w) risk and weaker tracking.
  • Hybrid (short links now, Special Links at scale) — Ship immediately, de-risk later; two link formats to manage.

Recommendation: Replace with tagged Special Links before scaling. Test one link per product in the enrolled Associates workflow and confirm the destination and tracking report before scaling.

How to find out: Log into Associates Central, generate a Special Link for each resolved ASIN, and open each once to confirm the destination and that the click appears in the tracking report.

Question Q2

How do we display star ratings and review counts for the products whose ratings we could not capture?

What we know: ThermoMaven's rating was captured from the official listing (4.6 stars, 3,499 ratings). The other four ratings are displayed on their listings but were not captured in this extraction. Program Policies 6(t) restricts displaying Amazon customer reviews or star ratings unless obtained via Creators API or PA API.

What we do not know: Whether the account has Creators/PA API access; the exact numeric ratings for the four products.

Options

  • Show rating only where captured; blank + flag the rest — Fully honest; the comparison table looks uneven.
  • Point the rating cell to the listing ('see listing') — Reader can verify; not a stored value.
  • Pull ratings via Creators/PA API — Compliant and complete; requires API access and compliance with the License.

Recommendation: Show the captured rating and leave the four uncaptured ratings blank with a flag. Do not infer values.

How to find out: Request Creators/PA API access through Associates Central and pull ratings through the official API if granted.

Question Q3

How do we display prices under the Program Policies price-display rule?

What we know: Buy-box prices were read from each official listing on 2026-11-19. Program Policies 2(b) states prices and availability may only be shown if (a) Amazon serves the link with that price data, or (b) the data is obtained via Creators API or PA API.

What we do not know: Whether the links we publish will be Amazon-served price links or static; API access status.

Options

  • Show 'as listed' price with a live listing link and a verify date — Transparent; price may drift, so a date and a link are required.
  • Remove prices entirely — Maximum compliance; weaker buyer signal.
  • API-driven live price — Accurate and compliant; requires API access.

Recommendation: Show the price as listed, label it 'as listed on 2026-11-19', and link to the live listing so the reader sees the current price. Do not present a price comparison against non-Amazon sellers.

How to find out: Confirm whether the published links will be Amazon-served price links, or obtain Creators/PA API access for live pricing.

Question Q4

Where does the self-hosted analytics endpoint run, given GitHub Pages is static?

What we know: The site is served statically from GitHub Pages, which cannot receive POST requests. The five events (page_view, cta_click, product_click, filter_apply, guide_read) are defined and the client counter is built.

What we do not know: The chosen hosting for the collection endpoint.

Options

  • Serverless function at /collect (Netlify / Vercel / Deno) — Self-hosted, privacy-preserving, no third party; needs a small deploy.
  • Self-hosted Plausible — Purpose-built privacy analytics; more setup.
  • Client-only local counter — No server needed; data stays on the client and is not aggregated.

Recommendation: Deploy a small serverless /collect function alongside the static site and point the counter at it. Keep the counter cookie-free and store only an anonymous local ID.

How to find out: Choose the hosting for the endpoint and confirm the privacy posture (no cookies, no cross-site tracking).

Question Q5

What imagery do we use, given the Operating Agreement treats images as Program Content?

What we know: Operating Agreement §1 treats data, images and text as Program Content. Generated or copied photography is not permitted. S-18 (real product photography) needs a decision first.

What we do not know: Which official imagery channels are permitted for our use; whether brand press assets are usable.

Options

  • Text-led, no product photos for now — Safe and clean; less visual.
  • Use only Amazon-served/Program Content imagery per the Agreement — Compliant; limited styling control.
  • Commission original product photography — Strong and original; cost and lead time.

Recommendation: Stay text-led and editorial now. Add imagery only through an officially permitted channel once confirmed.

How to find out: Confirm with the Operating Agreement and Program Policies which imagery is permitted, then source accordingly.

Question Q6

What is the publishing cadence, and which guides go first?

What we know: Eight question-shaped guides are drafted. The site has a sitemap and RSS feed ready to accept each new guide.

What we do not know: Measured query demand — we have no analytics yet, so topic priority is currently editorial.

Options

  • Publish all eight now — Full library immediately; no measured prioritization.
  • Publish in phases, reorder by measured queries — Data-led ordering; needs analytics first.
  • Publish a weekly cadence with one new guide each week — Consistent; slow to build volume.

Recommendation: Publish the eight guides on a weekly cadence, then reorder the next topics from measured queries in Search Console and the analytics endpoint rather than instinct.

How to find out: Turn on Search Console and the analytics endpoint, then read the real query and click data after the first weeks.
